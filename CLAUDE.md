# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

`desktop/` — офлайн-обработка данных (на Mac) сканера **Pulse** из монорепо `../`. Velodyne VLP-16 стоит на вращающейся платформе. Bag'и записываются на Orange Pi (`../orangepi/`), мотор платформы управляется RP2040 (`../firmware/spin_controller`). Скрипты превращают MCAP-bag в зарегистрированное облако точек и экспорт для CAD. ROS для этого не нужен: bag читается через `mcap` + `mcap-ros2-support`.

Задачи уровня репо — `../Makefile`: `make sync-bags` (bag'и с Pi → `../bags/`), `deploy*`, `flash-*`, `logs-*`.

## Геометрия сканера (360×360)

Два вращения:

1. **Внутреннее вращение VLP-16**: 16 лучей с вертикальным FOV ±15° крутятся вокруг собственной оси Z лидара. Частота 10 Гц (600 RPM, кадр ≈ 100 мс).
2. **Вращение платформы** вокруг **вертикальной** оси мира, ~40 RPM (~240°/с, ~24° за кадр лидара). Лидар лежит на боку, поэтому вертикаль мира — это **ось X лидара**, отсюда `ROTATION_AXIS = 'x'`.

Плоскость сканирования лидара проходит через вертикаль. Поэтому за пол-оборота платформы покрывается вся сфера, а за полный оборот каждая точка снимается дважды. Расхождение двух половин — главный индикатор ошибок калибровки и биения оси.

Цепочка TF на Pi (`../orangepi/ros2/slam_bringup/launch/slam_scanner.launch.py`); во всех фреймах платформы X направлена вверх:
`world → imu_link → platform_base [z −25 мм] → platform_rotating (вращение вокруг X) → velodyne [x +165 мм вдоль оси, z +10.8 мм эксцентриситет, yaw −1.6°]`

В офлайн-коде это `ROTATION_CENTER = [0, 0, -0.0108]` и `MOUNT_RPY_DEG = [0, 0, -1.6]`. При изменении калибровки **синхронизировать оба места**.

**Вертикаль зависит от источника облака** (проверено 2026-10-01):
- `world_map.py` / `icp_merge.py` / `offline_deskew.py` выдают облако в системе лидара при θ платформы = 0, где **X — вертикаль**. Коррекция наклона по IMU в `world_map.py` ожидает g вдоль +X.
- Экспорт из HMI на Pi (`orangepi/hmi/app.py` → `bag_preview.py`; так получены, например, `static_YYYYMMDD_*.e57`) поворачивает облако по ориентации IMU (Madgwick с магнитометром). Вертикаль у такого облака — Z, но **направлена вниз: «вверх» = −Z**, хотя комментарий в `app.py` обещает Z-вверх. Проверено на `static_20260922_*`: земля у фасадов на Z ≈ +1.4, здание уходит до Z ≈ −17; потолок в комнатах на Z ≈ −1.5 (подтверждено пользователем), пол на Z ≈ +1.4. Вероятно, это ошибка знака в экспорте; без согласования с пользователем не исправлять. Поворот вокруг вертикали между сканами **не согласован**: преобладающее направление стен у сканов одного здания разное (7°…89° mod 90°). Его ищет `plane_register.py`.

Прежде чем работать с облаком, определите вертикаль **со знаком**. Пол и потолок дают пики в гистограмме по вертикальной оси. Различить их помогают:
- высота лидара над полом/землёй ~1.4 м (штатив);
- снаружи земля — самый большой горизонтальный слой, а здание уходит «вверх». Во `flythrough.py` облако поворачивают клавишами F5–F10.

## Окружение

```bash
source .venv/bin/activate      # venv на Python 3.14
pip install -r requirements.txt
```

В venv стоит Open3D 0.20, он работает на Python 3.14. Утверждение README, что Open3D не поддерживает 3.13+, устарело. Без Open3D работают `offline_deskew.py` и `world_map.py`. Тестов, линтера и сборки нет. Изменения проверяют прогоном на реальном bag из `../bags/` (имена `static_YYYYMMDD_HHMMSS/`) и визуально, во `flythrough.py` или CloudCompare.

## Команды

```bash
python world_map.py ../bags/<bag> [-o out.e57|.pcd] [--voxel 0.01]  # основной путь: deskew + коррекция наклона по IMU
python icp_merge.py ../bags/<bag> [--slices 12 --overlap 2.0 --fine --trim-end N] -o map.pcd
python offline_deskew.py <bag_dir|file.mcap[.zstd]> [out.npz]        # только deskew, по кадрам
python flythrough.py a.pcd [b.pcd ...]                                # вьювер; 2+ файла = сравнение / ручное выравнивание / pick-ICP
python evaluate_accuracy.py [e57_dir | a.e57 b.e57]                   # RMS плоскостей (RANSAC) + повторяемость через ICP
python export_cad.py in.pcd --format e57|las|xyz|pts|all
python export_mesh.py in.pcd --format obj|stl|dxf|all --depth 9       # Poisson-меш
```

Стыковка статических сканов по плоскостям (`planes.py`, `openings.py`, `plane_register.py`, `scan_project.py`; план и результаты — `docs/plan_plane_registration.md`):

```bash
python scan_project.py build static_*.e57 -o X.project.json [--reuse old.project.json]  # авто: пары → граф → позы
python scan_project.py view X.project.json -o top.png       # вид сверху для проверки
python scan_project.py merge X.project.json -o merged.e57   # склейка в системе опорного скана
python scan_project.py openings X.project.json              # проёмы с номерами
python scan_project.py attach X.project.json FACADE.e57 --pair ROOM.e57:K M   # ручная привязка по паре окон
python reflections.py scan.e57 [-o clean.ply]               # удалить зеркальные отражения (стёкла, глянцевый пол)
python -m unittest discover -s tests -v                     # синтетические тесты (лучевая «съёмка» комнаты)
```

**Стёкла дают зеркальные «призраки» помещений** (за окном — копия комнаты). `merge`/`view` убирают их по умолчанию через `reflections.py`. При анализе сырых сканов учитывайте, что такие точки в них есть.

Внутри стыковки всё считается в «канонической» системе скана: +Z вверх, начало — сканер. Вертикаль со знаком определяется по мёртвому конусу под штативом (`planes.detect_up`). Позы в `*.project.json` переводят точки скана **в его исходной системе** в исходную систему опорного скана; исходные файлы не меняются.

Полный список флагов и клавиш вьювера — в `README.md`.

## Архитектура

- **`offline_deskew.py` — единственный источник математики deskew и калибровки.** Этот репо подключён к монорепо как сабмодуль `desktop/`, а `../shared/offline_deskew.py` — симлинк на этот файл. `../scripts/deploy.sh` и OTA (`orangepi/scripts/update.sh`) копируют его на Pi (`~/hmi/offline_deskew.py`, `rsync -L`), где на нём работает превью bag'ов в HMI, так что правка влияет и на Pi. `../orangepi/hmi/offline_deskew.py` — отдельная устаревающая копия; её не править.
- `world_map.py` и `icp_merge.py` импортируют из `offline_deskew` функции `read_bag`, `parse_pointcloud2`, `deskew_cloud` и константы калибровки. Запускать их нужно из этой директории.
- **Топики bag'а**:
  - `/velodyne_points` (PointCloud2, 10 Гц, есть поле `time` для каждой точки);
  - `/rotating_platform/joint_state` (JointState, 100 Гц, `position[0]` — непрерывный угол в радианах);
  - `/rotating_platform/angle` (Float64, запасной источник);
  - `/rotating_platform/velocity`;
  - `/imu` (на Pi ремап из `/imu/data_raw`).
- **Время** (`read_bag`):
  - Временная ось угла — `log_time` bag'а (часы хоста, тот же домен, что у velodyne), а **не** `header.stamp` JointState: часы RP2040 уходят примерно на 7 мс/с.
  - Регрессия RP2040→хост считается только для диагностики RMS.
  - Fallback на Float64 даёт джиттер ~20 мс.
- **Deskew** (`deskew_cloud`, абсолютный, как в PandarMapper):
  - `header.stamp` VLP-16 — **конец** кадра, а `time` точки **отрицательный** (от −0.1 до 0 с).
  - Для каждой точки угол платформы интерполируется в момент `stamp + time`.
  - Затем точка переводится в мир θ=0: mount-оси → mount-RPY → сдвиг на `ROTATION_CENTER` → поворот на `-θ - ANGLE_OFFSET` вокруг оси → обратные преобразования.
  - Отдельный «мировой» поворот после deskew **не нужен**.
- **`world_map.py`**:
  - Отбрасывает кадры, если за 110 мс до них меньше 5 сэмплов энкодера.
  - Фильтрует точки по дальности (0.3–20 м).
  - По первым ~500 сэмплам `/imu` строит поворот Родрига: IMU стоит X-вверх, ожидаемое g ≈ [+1, 0, 0]. Этот поворот убирает наклон основания (типично ~3°), иначе вместо сцены получается «воронка».
  - Вокселизирует облако на numpy.
- **`icp_merge.py`**:
  - Делит оборот на N угловых срезов. Каждый срез берёт окно `overlap × 360/N`, а в итоговое облако отдаёт только ядро 360/N.
  - Выравнивает срезы ICP в два прохода (point-to-point → point-to-plane): цепочка → уточнение → повторная цепочка.
  - Нужен для компенсации механики (биение вала, люфт), которую deskew не исправляет.
- `.mcap.zstd` при первом чтении распаковывается рядом с оригиналом (`resolve_mcap_path`).

## Подводные камни (подтверждено опытом)

- **Направление вращения VLP-16 должно быть +RPM** (~+600). При отрицательном RPM комната получается зеркальной. Раньше это маскировали связкой `INVERT_ROTATION=True` и flip по Y; две ошибки компенсировали друг друга. Сейчас `INVERT_ROTATION=False`, flip'ов нет. Возвращать их не надо.
- `MOUNT_AXES` с минусами и любые flip'ы осей ломают геометрию. Flip до коррекции наклона даёт неверный Z.
- «Закрученное» облако обычно означает проблему синхронизации времени (часы RP2040, джиттер чтения UART) или неверную ось вращения.
- «Воронка» — это наклон оси платформы. Статический наклон исправляется по IMU. Остаток (~1° биения оси во время вращения) имеет физическую природу; частично его снимает `icp_merge`.
- Дефолты в таблицах README (`ANGLE_OFFSET_DEG=184`, `ROTATION_CENTER=[0,0,0]`) устарели. Верить нужно коду `shared/offline_deskew.py`.
- Достигнутая точность: RMS плоскости ±15 мм, P95 ±27 мм.
