# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

`desktop/` — офлайн-обработка данных (на Mac) сканера **Pulse** из монорепо `../`. Velodyne VLP-16 стоит на вращающейся платформе. Bag'и записываются на Orange Pi (`../orangepi/`), мотор платформы управляется RP2040 (`../firmware/spin_controller`). Скрипты превращают MCAP-bag в зарегистрированное облако точек и экспорт для CAD. ROS для этого не нужен: bag читается через `mcap` + `mcap-ros2-support`.

Задачи уровня репо — `../Makefile`: `make sync-bags` (bag'и с Pi → `../bags/`), `deploy*`, `flash-*`, `logs-*`.

## Геометрия сканера (360×360)

Два вращения:

1. **Внутреннее вращение VLP-16**: 16 лучей с вертикальным FOV ±15° крутятся вокруг собственной оси Z лидара. Частота 10 Гц (600 RPM, кадр ≈ 100 мс).
2. **Вращение платформы** вокруг **вертикальной** оси мира, ~40 RPM (~240°/с, ~24° за кадр лидара). Лидар лежит на боку, поэтому вертикаль мира — это **ось X лидара**, отсюда `ROTATION_AXIS = 'x'`.

Плоскость сканирования лидара проходит через вертикаль. Поэтому за пол-оборота платформы покрывается вся сфера, а за полный оборот каждая точка снимается дважды. Расхождение двух половин — главный индикатор ошибок калибровки и биения оси.

Цепочка TF на Pi (`../orangepi/ros2/slam_bringup/launch/slam_scanner.launch.py`); во всех фреймах платформы X направлена вверх:
`world → imu_link → platform_base [z −25 мм] → platform_rotating (вращение вокруг X) → velodyne [x +165 мм вдоль оси, z +10.8 мм эксцентриситет, yaw −1.6°]`

В офлайн-коде это `ROTATION_CENTER = [0, 0, -0.0108]` и `MOUNT_RPY_DEG = [0, 0, -1.6]`. При изменении калибровки **синхронизировать оба места**.

**Вертикаль зависит от источника облака** (проверено 2026-10-01):
- `world_map.py` / `icp_merge.py` / `offline_deskew.py` выдают облако в системе лидара при θ платформы = 0, где **X — вертикаль**. Коррекция наклона по IMU в `world_map.py` ожидает g вдоль +X.
- Экспорт из HMI на Pi (`orangepi/hmi/app.py` → `bag_preview.py`; так получены, например, `static_YYYYMMDD_*.e57`) поворачивает облако по ориентации IMU (Madgwick с магнитометром). Вертикаль у такого облака — Z, но **направлена вниз: «вверх» = −Z**, хотя комментарий в `app.py` обещает Z-вверх. Проверено на `static_20260922_*`: земля у фасадов на Z ≈ +1.4, здание уходит до Z ≈ −17; потолок в комнатах на Z ≈ −1.5 (подтверждено пользователем), пол на Z ≈ +1.4. Вероятно, это ошибка знака в экспорте; без согласования с пользователем не исправлять. Поворот вокруг вертикали между сканами **не согласован**: преобладающее направление стен у сканов одного здания разное (7°…89° mod 90°). Его ищет `plane_register.py`.

**Сканы экспорта HMI систематически наклонены на ~3.7–5.6°** (проверено 2026-10-02 на `static_20260922_*`). Ось наклона почти одна и та же в системе сканера, поэтому это, вероятно, смещение IMU или крепления, а не шум. Компенсация: `level_correction` / `Session.level_pose` / `Session.level_project`, в GUI — кнопки выравнивания. Позы между внутренними сканами решает 6-DOF ICP, поэтому общий наклон группы снимается выравниванием проекта. Источник наклона на Pi не исправлен.

Прежде чем работать с облаком, определите вертикаль **со знаком**. Пол и потолок дают пики в гистограмме по вертикальной оси. Различить их помогают:
- высота лидара над полом/землёй ~1.4 м (штатив);
- снаружи земля — самый большой горизонтальный слой, а здание уходит «вверх». Во `flythrough.py` облако поворачивают клавишами F5–F10.

## Окружение

```bash
.venv312/bin/python ...        # Python 3.12 + Open3D 0.19.0 — основное окружение (GUI работает)
.venv/bin/python ...           # Python 3.14 + Open3D 0.20 — CLI работает, но окно GUI чёрное
```

**Open3D закреплён на 0.19.0** (`requirements.txt`): в 0.20 нативное окно и режим `--web` показывают чёрный экран с артефактами на macOS 15.5 + Metal (M1 Max). При этом `render_to_image` работает — вероятно, из-за нового вывода SceneWidget через текстуру (см. Open3D #7446). Колёса 0.19.0 есть только для Python ≤3.12.

**Целевые платформы — macOS, Windows, Linux.** Не используйте платформенно-зависимые вызовы без ветвления по `platform.system()` (см. `scan_gui.screen_size`, `capture_window`, `find_font`). Файлы читайте и пишите с `encoding='utf-8'`. В проектах храните пути относительно файла проекта (`scan_project.rel_path` / `abs_path`). CI: `.github/workflows/tests.yml` запускает тесты на трёх ОС.

**Esc в Open3D закрывает окно** (`Window::OnKeyEvent` вызывает `Close()` раньше обработчика клавиш). Защита — `set_on_close`: окно закрывается только после подтверждения, а Esc распознаётся по времени последнего нажатия (`scan_gui._on_close`).

**Шрифт GUI.** В Open3D 0.19 `add_typeface_for_code_points` не работает (выводит «?»). Кириллица подключается через `add_typeface_for_language(path, 'ru')`: любой «неизвестный» код языка даёт диапазон латиница + кириллица. Символы вне него (стрелки, ✓, ⌘, длинное тире) не отрисуются, поэтому в текстах интерфейса их не используйте. Без Open3D работают `offline_deskew.py` и `world_map.py`. Тестов, линтера и сборки нет. Изменения проверяют прогоном на реальном bag из `../bags/` (имена `static_YYYYMMDD_HHMMSS/`) и визуально, во `flythrough.py` или CloudCompare.

## Команды

```bash
python world_map.py ../bags/<bag> [-o out.e57|.pcd] [--voxel 0.01]  # основной путь: deskew + коррекция наклона по IMU
python icp_merge.py ../bags/<bag> [--slices 12 --overlap 2.0 --fine --trim-end N] -o map.pcd
python offline_deskew.py <bag_dir|file.mcap[.zstd]> [out.npz]        # только deskew, по кадрам
python flythrough.py a.pcd [b.pcd ...]                                # вьювер; 2+ файла = сравнение / ручное выравнивание / pick-ICP
python evaluate_accuracy.py [e57_dir | a.e57 b.e57]                   # RMS плоскостей (RANSAC) + повторяемость через ICP
python export_cad.py in.pcd --format e57|las|xyz|pts|all
python export_mesh.py in.pcd --format obj|stl|dxf|all --depth 9       # Poisson-меш
```

Стыковка статических сканов по плоскостям (`planes.py`, `openings.py`, `plane_register.py`, `scan_project.py`; план и результаты — `docs/plan_plane_registration.md`):

```bash
python scan_project.py build static_*.e57 -o X.project.json [--reuse old.project.json]  # авто: пары → граф → позы
python scan_project.py view X.project.json -o top.png       # вид сверху для проверки
python scan_project.py merge X.project.json -o merged.e57   # склейка в системе опорного скана
python scan_project.py openings X.project.json              # проёмы с номерами
python scan_project.py attach X.project.json FACADE.e57 --pair ROOM.e57:K M   # ручная привязка по паре окон
python reflections.py scan.e57 [-o clean.ply]               # удалить зеркальные отражения (стёкла, глянцевый пол)
python scan_gui.py X.project.json | scan1.e57 scan2.e57 …   # интерактивный инструмент (Open3D GUI)
python tests/gui_smoke.py X.project.json OUT_DIR [--candidates SCAN]  # сквозная проверка окна без человека (снимки сцены в OUT_DIR)
python -m unittest discover -s tests -v                     # синтетические тесты (лучевая «съёмка» комнаты)
```

**Стёкла дают зеркальные «призраки» помещений** (за окном — копия комнаты). `merge`/`view` убирают их по умолчанию через `reflections.py`. При анализе сырых сканов учитывайте, что такие точки в них есть.

**Калибровка устройства при реконструкции** — `calibration.py`.
- Порядок источников: топик `/pulse/calibration` в bag'е (`std_msgs/String` с JSON калибровки Pi; формат `calib.json` веб-HMI тоже понимается: `mount_yaw_deg`, `R`, `tilt_deg`); иначе таблица `HISTORY` по дате записи из имени; ручная поправка yaw (`mount_yaw_deg`) поверх.
- Кронштейн лидара заменён между 2026-10-02 и 2026-10-04: yaw −1.6° → −0.6° (подобрано `calibrate_mount.py` по совпадению полуоборотов).
- `bag_reconstruct.reconstruct` передаёт эти параметры в deskew явно, глобальные `offline_deskew.MOUNT_RPY_DEG` на импорт не влияют. Калибровка пишется в метаданные скана (`calibration`), её отпечаток — в `params` (`expected_params`): смена калибровки запускает пересчёт при переимпорте. Наклон `tilt='calib'` берёт `tilt_R` из калибровки (если её нет — выравнивание по геометрии).

Импорт со сканера — `scanner_client.py`: только urllib, `pulse.local:80`. Файлы bag отдаёт веб-HMI через `orangepi/hmi/bag_files.py` (Blueprint без ROS, подключён в `app.py`; Range для докачки). Импорт bag в GUI — `bag_reconstruct.py`. Это та же математика, что `world_map.py`: deskew `offline_deskew` по `log_time`, но наклон оси по умолчанию исправляется по геометрии (пол и стены), а не по IMU. **Плату IMU переставили, сейчас она стоит осью Z вверх; `world_map.read_imu_tilt` рассчитан на X вверх и даёт поворот ~90°.** Выход реконструкции — система лидара при θ=0 (вертикаль +X). Запускалки: `run_gui.command` / `.sh` / `.bat` (окружение `.venv312`).

**Передача проекта** — `Session.pack(dest, as_zip)`. В папку или zip попадают: `<имя>.pulse`, `scans/` (сканы с их `.json` / `.dyn.npy`), полный кеш анализа и `ПРОЧТИ.txt`; пути относительные, открытый сеанс не меняется. Ключ кеша (`project_store.scan_key`) содержит `qhash` — md5 первого и последнего мегабайта. При совпадении суммы дата файла не проверяется: после распаковки zip время файлов другое. Старые ключи без суммы сравниваются по дате.

Интерактивный инструмент: `scan_gui.py` — тонкий слой окна над `scan_session.py`. Проект — `.pulse` (zip: `project.json` + `cache/<скан>/meta.json, arrays.npz`, модуль `project_store.py`); `scan_project.load_project/save_project` читают и пишут оба формата, сохраняя кеш. **При изменении `planes` / `openings` / `reflections`, влияющем на результат, увеличьте `project_store.CACHE_VERSION`**, иначе останется старый кеш. Анализ скана ленивый и потокобезопасный (`Scan._lock`): GUI сначала показывает сканы (`Scan.quick_points` или кеш), затем анализирует в фоне (`App._analyze_bg`) и пишет кеш в архив (`Session.flush_cache`, `project.json` не трогает). Иерархия сканов — `scan_tree.py` (`Session.tree`, поле `tree` в project.json): только организация, видимость и выбор подмножеств, на геометрию не влияет. Видимость скана — флаг скана и всех предков (`Session.apply_visibility`). Временный показ пары или ручного режима запоминает и восстанавливает видимость дерева. Ручная чистка — `manual_clean.py`: прямоугольник на экране превращается в 4 боковые плоскости пирамиды взгляда. Области хранятся у скана (`Scan.erase`, канон. система, в project.json — `erase`) и применяются в `Scan.down` и при экспорте полного разрешения. Куб навигации — `view_cube.py` (рисование через Pillow, попадание мышью, привязка). Это порт куба из `orangepi/hmi/templates/preview.html`, но в системе Z-вверх. В окне он показан фоном отдельного маленького `SceneWidget` поверх основного: в Open3D нет 2D-холста, а верхний виджет получает мышь в своей области. Вся логика сеанса (проект, рёбра с ручными принять/отклонить, ручные пары признаков, кандидаты, чистка, экспорт) находится в `scan_session.py` и тестируется без окна (`tests/test_session.py`). Новую функциональность добавляйте туда, а в окно — только виджеты и вызовы. Сцена окна рисуется в общей системе: каноническая система опорного скана, Z вверх. Окно на этой машине не видно агенту (у терминала нет записи экрана). Проверяйте через `tests/gui_smoke.py`: он вызывает обработчики и сохраняет `render_to_image` сцены.

**Новое окно — `scan_qt.py` + пакет `pulse_qt/` (Qt / PySide6 + VTK, ветка `feature/qt-ui`).** Тот же слой над `scan_session.py`, что и `scan_gui.py`; старое окно не трогаем, пока новое не заменит его. Устройство:
- `cloud_view.py` — 3D-вид: VTK рисует **вне экрана** (`SetOffScreenRendering`), кадр читается в QImage (`Format_RGBX8888` — альфа фона у VTK 0) и рисуется в `paintEvent`. Встроенный `QVTKRenderWindowInteractor` в Python всегда создаёт нативное окно (даже с `QVTKRWIBase='QOpenGLWidget'`): поверх него не лягут плашки, а `grab()` даёт чёрный кадр. Навигация своя (поворотный стол вокруг Z, сдвиг, масштаб к курсору); режимы окна перехватывают мышь через `CloudView.mouse_hook`. Выбор точки — проекцией точек облаков на экран (`pick_point`), не через буфер глубины. Камера отдаёт базис `basis()` в той же форме, что `get_model_matrix` у Open3D, поэтому `view_cube.py` общий (у `ViewCube` добавлены `style` и `render(..., rgba=True)`).
- **Лента** (`ribbon.py`, `MainWindow._topbar`): вкладки-этапы Проект / Стыковка / Контроль / Чистка / Результат. На ленте команды, в правой панели — параметры и состояние. Вкладка открывает свою панель (`on_tab`), смена режима переключает вкладку (`_sync_ribbon`, вызывается из `_banner`). Кнопки вида — на плашке 3D-вида.
- `main_window.py` — контроллер (перенос методов `scan_gui.App`); `tree_panel.py`, `inspector.py` (инспектор / ручная / чистка), `dock.py`, `dialogs.py`, `widgets.py` — виджеты; `theme.py` — палитры макета (OKLCH → sRGB), таблица стилей, шрифты IBM Plex (`pulse_qt/fonts`, OFL), значки MDI через qtawesome. Тема меняется пересборкой окна (`toggle_theme`): значки рисуются цветами темы при создании.
- Фоновые задачи — `bg.run` / `bg.post` (результат в главном потоке через сигнал Qt).
- **Стыковка групп.**
  - «Внутри групп»: `Session.within_group_pairs` → `run_auto(combos=...)`.
  - «Группы между собой»: `Session.register_groups`. Группа собирается в жёсткое облако по своим связям (`group_frame` / `group_res`, работает и без связи с опорным сканом). Гипотезы: плоскости объединённых облаков, пары крупнейших сканов групп, текущая поза. Каждая уточняется ICP по объединённым облакам и оценивается `ConsistencyScorer`; лучшая становится ребром `method='group'` между главными сканами.
  - Рёбра 'group' и 'manual' `run_auto` сохраняет. Одна только оценка по плоскостям объединённых облаков правильную позу на реальных комнатах не находила.
- **Нулевой уровень и замеры** — `measure.py` (вычисления, подписи) и `pulse_qt/control_panel.py` (вкладка «Контроль», режим `control`).
  - `Session.zero` (`{'z', 'source'}`, общая система; `None` — пол опорного скана, `measure.default_zero`) и `Session.measures` (точки в общей системе) хранятся в project.json.
  - Точка ставится щелчком без перетаскивания (`MainWindow.measure_click` → `measure_point`); перетаскивание по-прежнему вращает вид.
  - Подписи — плашки Qt над 3D-видом (`Viewport.set_labels`), сетка 1 м лежит на нулевом уровне.
- **Сечения** — `section.py`.
  - Режимы: срез (полоса толщиной `thick`) и отсечение (одна сторона; `flip`).
  - Основа: Z (положение — отметка от нулевого уровня), X, Y или найденная плоскость; доворот углами `a`, `b` вокруг осей плоскости (`section.axes`).
  - Отрисовка — плоскости отсечения VTK на всех актёрах (`CloudView.set_section`), кроме служебных префиксов `NO_SECTION`. Плоскости VTK задаются в мировой системе; позу облака (`UserMatrix`) VTK учитывает сам.
  - `pick_point` выбирает только видимые точки. Состояние лежит в `Session.section` (project.json).
  - Транспортиры опорной точки и сечения — общий код (`MainWindow._protractor`, `_draw_rings`).
- **Уточнение стыковки.**
  - Автоподгонка: `Session.refine_icp(..., wide=True)`, захват 0.6 → 0.25 → 0.08 м, по умолчанию к неподвижному скану; ICP ко всем размещённым хуже для фасадов.
  - Опорная точка: `center=...` → `plane_register.refine_rotation`, линеаризованная точка-плоскость только по повороту, точка остаётся на месте. Повороты вокруг точки — `Session.rotate_about` / `pr.rotate_about`, R = Rz·Ry·Rx; углы в окне отсчитываются от позы при закреплении (`MainWindow.pivot`).
  - Принятая после автоподгонки связь получает `weight` (×10, `ICP_WEIGHT`) в `recompute_poses`: иначе граф сводит её с грубыми ручными связями поровну.
  - Оценка подгонки — `Session.pair_thickness`: `quality.plane_cells` с подменой поз (`poses=`), сеанс при этом не меняется.
- **Качество совмещения** — `quality.py`. Есть два способа: `plane_cells` (общие плоскости разных сканов, медианы по ячейкам 20 см) и `local_cells` (воксели 20 см, плоские у каждого скана). Толщина считается один раз, порог только перекрашивает. Подсветка рисуется верхним слоем VTK (`set_cloud(..., on_top=True)`, `CloudView.ren_top`).
- **Движущиеся объекты** — `dynamic.py`.
  - По полуоборотам: карты дальности на каждый проход при реконструкции из bag (`bag_reconstruct.process_frames`). Результат лежит рядом со сканом в `<скан>.dyn.npy` в порядке точек файла; `dyn_version` в `params` нужен, чтобы повторный импорт пересчитывал скан.
  - Между сканами: `RangeImage.masks` других размещённых сканов. Большие плоскости (≥ 3 м²) не отмечаются: их расхождение — это ошибка совмещения, а не движение.
  - Удаление — `Scan.drop` (ключи вокселей 5 см, `scan_session.voxel_keys`, поле `drop` в project.json). Оно применяется там же, где `erase`; отмена через `erase_undo` (записи `('drop', id, ключи)`).
- **Поверхность** — `surface.py`, экспериментальная. Нормали направлены на свой сканер. **PoissonRecon в Open3D 0.19 при «Failed to close loop» вызывает `exit()`**: процесс завершается с кодом 0, случайно, в многопоточном режиме. Поэтому сетка (оба метода) считается только в отдельном процессе (`surface._run_child`): Пуассон в один поток с повторами; процесс можно остановить (Esc, «Остановить»). Ball pivoting однопоточный и медленный — больше `BPA_MAX_POINTS` точек точность загрубляется. После построения точки сканов скрываются: сетка совпадает с точками и иначе в них не видна. Сетки хранятся в `Session.meshes`, только в памяти.
- Проверка без человека: `python tests/qt_smoke.py X.pulse OUT [--light]` (снимки состояний, сканер подменён заглушкой) и `python tests/qt_interact.py X.pulse` (события мыши: вращение, Ctrl+клик, перетаскивание скана, рамка, полёт). Окно на время теста появляется на экране.

Внутри стыковки всё считается в «канонической» системе скана: +Z вверх, начало — сканер. Вертикаль со знаком определяется по мёртвому конусу под штативом (`planes.detect_up`). Позы в `*.project.json` переводят точки скана **в его исходной системе** в исходную систему опорного скана; исходные файлы не меняются.

Полный список флагов и клавиш вьювера — в `README.md`.

## Архитектура

- **`offline_deskew.py` — единственный источник математики deskew и калибровки.** Этот репо подключён к монорепо как сабмодуль `desktop/`, а `../shared/offline_deskew.py` — симлинк на этот файл. `../scripts/deploy.sh` и OTA (`orangepi/scripts/update.sh`) копируют его на Pi (`~/hmi/offline_deskew.py`, `rsync -L`), где на нём работает превью bag'ов в HMI, так что правка влияет и на Pi. `../orangepi/hmi/offline_deskew.py` — отдельная устаревающая копия; её не править.
- `world_map.py` и `icp_merge.py` импортируют из `offline_deskew` функции `read_bag`, `parse_pointcloud2`, `deskew_cloud` и константы калибровки. Запускать их нужно из этой директории.
- **Топики bag'а**:
  - `/velodyne_points` (PointCloud2, 10 Гц, есть поле `time` для каждой точки);
  - `/rotating_platform/joint_state` (JointState, 100 Гц, `position[0]` — непрерывный угол в радианах);
  - `/rotating_platform/angle` (Float64, запасной источник);
  - `/rotating_platform/velocity`;
  - `/imu` (на Pi ремап из `/imu/data_raw`).
- **Время** (`read_bag`):
  - Временная ось угла — `log_time` bag'а (часы хоста, тот же домен, что у velodyne), а **не** `header.stamp` JointState: часы RP2040 уходят примерно на 7 мс/с.
  - Регрессия RP2040→хост считается только для диагностики RMS.
  - Fallback на Float64 даёт джиттер ~20 мс.
- **Deskew** (`deskew_cloud`, абсолютный, как в PandarMapper):
  - `header.stamp` VLP-16 — **конец** кадра, а `time` точки **отрицательный** (от −0.1 до 0 с).
  - Для каждой точки угол платформы интерполируется в момент `stamp + time`.
  - Затем точка переводится в мир θ=0: mount-оси → mount-RPY → сдвиг на `ROTATION_CENTER` → поворот на `-θ - ANGLE_OFFSET` вокруг оси → обратные преобразования.
  - Отдельный «мировой» поворот после deskew **не нужен**.
- **`world_map.py`**:
  - Отбрасывает кадры, если за 110 мс до них меньше 5 сэмплов энкодера.
  - Фильтрует точки по дальности (0.3–20 м).
  - По первым ~500 сэмплам `/imu` строит поворот Родрига: IMU стоит X-вверх, ожидаемое g ≈ [+1, 0, 0]. Этот поворот убирает наклон основания (типично ~3°), иначе вместо сцены получается «воронка».
  - Вокселизирует облако на numpy.
- **`icp_merge.py`**:
  - Делит оборот на N угловых срезов. Каждый срез берёт окно `overlap × 360/N`, а в итоговое облако отдаёт только ядро 360/N.
  - Выравнивает срезы ICP в два прохода (point-to-point → point-to-plane): цепочка → уточнение → повторная цепочка.
  - Нужен для компенсации механики (биение вала, люфт), которую deskew не исправляет.
- `.mcap.zstd` при первом чтении распаковывается рядом с оригиналом (`resolve_mcap_path`).

## Подводные камни (подтверждено опытом)

- **Направление вращения VLP-16 должно быть +RPM** (~+600). При отрицательном RPM комната получается зеркальной. Раньше это маскировали связкой `INVERT_ROTATION=True` и flip по Y; две ошибки компенсировали друг друга. Сейчас `INVERT_ROTATION=False`, flip'ов нет. Возвращать их не надо.
- `MOUNT_AXES` с минусами и любые flip'ы осей ломают геометрию. Flip до коррекции наклона даёт неверный Z.
- «Закрученное» облако обычно означает проблему синхронизации времени (часы RP2040, джиттер чтения UART) или неверную ось вращения.
- «Воронка» — это наклон оси платформы. Статический наклон исправляется по IMU. Остаток (~1° биения оси во время вращения) имеет физическую природу; частично его снимает `icp_merge`.
- Дефолты в таблицах README (`ANGLE_OFFSET_DEG=184`, `ROTATION_CENTER=[0,0,0]`) устарели. Верить нужно коду `shared/offline_deskew.py`.
- Достигнутая точность: RMS плоскости ±15 мм, P95 ±27 мм.
